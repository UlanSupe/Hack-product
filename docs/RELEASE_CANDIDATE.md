# Release candidate review

Date: 2026-11-06. Scope: a release-readiness review of PactPay Arena as it exists in this repository. No product feature was added. Companion documents: [QA_REPORT.md](QA_REPORT.md) (the earlier quality pass), [SECURITY_REVIEW.md](SECURITY_REVIEW.md), [DEPLOYMENT.md](DEPLOYMENT.md), [PAYPAL_INTEGRATION.md](PAYPAL_INTEGRATION.md).

## 1. Verdict

**Release candidate for public evaluation of the code and of the simulated demonstration: yes, with the limits in sections 6 and 8.**

- No critical or high-severity defect was found, and every automated gate passed on a clean clone (section 3).
- The protected transaction path cannot reach PayPal without a fresh, server-side policy decision, and the unsafe baseline cannot reach anything except an in-memory simulated ledger (section 5).
- **Update 2026-11-08:** the PayPal Sandbox flow (create, buyer approval, hold, capture, reconciliation) was run live and a completed 60.00 USD sandbox capture was confirmed by an independent read from PayPal; two defects only the live service showed were fixed ([PAYPAL_INTEGRATION.md](PAYPAL_INTEGRATION.md) section 17). A separate hold-and-void and seven signed webhook deliveries over two runs (through a temporary tunnel; including void and refund) were run live too. Reversal, declined and pending capture webhooks were not. The earlier text of this document, written before that run, said none of the flow had been run against PayPal.
- Nothing is deployed. The public-demo smoke test below ran against a local process started the way Render starts it.
- This review was done by the engineer (an AI assistant) who wrote most of the code, with tests it also wrote. It found and fixed real problems, which shows the method works; it does not show that none remain.

## 5. Confirmations asked for

### 5.1 The protected transaction path cannot bypass policy enforcement

**Method:** trace from every call that can reach PayPal back to the policy decision that must precede it, then check the tests that pin each link. **Result: confirmed for the code as it stands, to the extent a review by the author and a test suite can confirm it.**

- **There is one door.** Only `src/application/payments.ts` calls the payment provider (`createOrder`, `authorizeOrder`, `captureAuthorization`, `voidAuthorization`, `getOrder`), and only `src/server/payment-service.ts` and the webhook composition root construct the provider. The provider interface has no refund, reauthorize or payout method. Tests: `test/payments/boundaries.test.ts` (only the composition roots import the adapter; domain and policy import no provider; the negotiation and mandate services cannot start a payment; no client component reaches PayPal; the PayPal secret is read in exactly three files).
- **Each money-moving step evaluates the policy first, on server-loaded facts, and a denial returns before any state change or provider call.** `start` (create order, `payments.ts` around line 972), `authorize` (around line 1242) and `capture` / `void` (around line 797) each call `evaluatePolicy(ops.policyInput(...))` inside the database transaction, record the decision, and on `DENY` write a `PAYMENT_POLICY_DENIED` audit event and return. Only an `ALLOW` goes on to move the transaction state (a compare-and-set on the version), write the attempt row, and then call PayPal. The amount, currency, payee and order ids sent to PayPal come from the stored agreement and transaction rows, never from the request: payment routes require an empty body.
- **Roles.** Capture is operator-only in the policy table; agents are refused at the route guard (`x-agent-id` / `authorization` headers refuse a signed-in request); the operator guard requires session, CSRF token and same origin. Tests: `test/security/route-sweep.test.ts` discovers every `route.ts` from the file system and fails if one is unclassified; the adversarial suite (124 scenarios) covers approval bypass, replay, duplicate requests, changed agreement after approval, mandate tampering, forged webhooks and malformed AI output.
- **A revoked mandate blocks capture**, as does an unverifiable payee, a lapsed honor period and a changed agreement (`test/payments/capture-flow.test.ts`, `test/flagship/capture-after-change.test.ts`). The mutation spot-check in [QA_REPORT.md](QA_REPORT.md) section 2 showed that deliberately letting an agent capture, skipping the CSRF check, disabling the same-origin check, dropping the amount comparisons and weakening webhook verification each made at least one test fail (9 of 9 mutants caught; not re-run in this review).
- **A webhook and the return URL cannot move money.** Both only trigger a fresh read of the order, which is applied through the same transition rules as the "Check status" button.

**Deliberate gaps, documented rather than hidden** ([SECURITY_REVIEW.md](SECURITY_REVIEW.md) section 4.2): capture does not require the _newest_ mandate version (a revoked one still blocks it); and policy is evaluated in the database transaction that records the attempt, so a change made in the few milliseconds before PayPal answers is not re-checked.

**What this does not establish:** that PayPal behaves as the adapter assumes (never run live); that no path exists that a reviewer who did not write the code would find.

### 5.2 The baseline is isolated and sandbox-only

**Result: confirmed.**

- The baseline's only way to spend is `executeUnchecked(proposal, ledger)` in `src/application/arena-baseline.ts`, whose parameter is a `SimulatedLedger` (an in-memory object with no credentials, no network and no PayPal id). The file imports only types from `domain/experiment.ts`; it has no provider, adapter, environment or server import. It is labelled `INTENTIONALLY UNSAFE BASELINE` in the source and `Unsafe by design` / `Simulated ledger only` in the UI.
- The layer rules (`eslint.boundaries.mjs`) stop `application/` importing adapters or server code, and stop `agents/` reaching anything with a path to money.
- The flagship replay runs on a throwaway `:memory:` database (`src/server/flagship.ts`).
- The database refuses an `UNSAFE_BASELINE` attack run that is not marked simulated or that has a transaction (migration `0004`).
- Tests: `test/arena/isolation.test.ts` scans the experiment's imports, proves a run makes no network call and ignores PayPal credentials even if set, checks that every settlement is a labelled simulated receipt and never a PayPal id, and checks the database constraint. The benchmark replaces `fetch` with a trap that fails the run, and a test asserts that.
- PayPal is sandbox-only for everything: the env parser rejects any `PAYPAL_ENV` other than `sandbox` and any non-sandbox API host, and the adapter has one hard-coded sandbox host.

## 9. Features intentionally excluded from the MVP

These are decisions recorded in [ARCHITECTURE.md](ARCHITECTURE.md) (non-goals), [PAYPAL_INTEGRATION.md](PAYPAL_INTEGRATION.md) and [COCKPIT.md](COCKPIT.md), not oversights:

- **Real money and production PayPal.** Sandbox only, in every mode; live PayPal is refused at startup.
- **Payouts to sellers, real or simulated.** The product never pays the seller, and no simulation of a payout exists in the code. Real Payouts API access is unresolved and kept separate from capture.
- **Escrow.** A PayPal authorization hold is not escrow and is never described as one.
- **Refunds, disputes, reauthorization, partial or multiple captures, multiple purchase units.** Full capture of the whole agreed total only. Non-USD payments are refused by the payment flow in this build.
- **Accounts and multi-tenancy.** One shared operator passcode; no per-user accounts, SSO, roles beyond operator/agent, or session revocation.
- **Automatic reconciliation timer.** An unknown outcome is settled when the operator presses "Check status" or a verified webhook arrives.
- **Offline webhook signature verification.** The endpoint uses PayPal's own verification call (postback) only.
- **AG Grid Enterprise, Integrated Charts, AG Studio and agent-generated widgets.** The Cockpit uses AG Grid Community only; no licence key.
- **A verified live-LLM buyer or seller.** The adapter exists and is off by default; it has not been run.
- **Scaling.** No multi-instance operation, external database or autoscaling; SQLite and in-process limits require exactly one instance.
- **A Content-Security-Policy.** Tracked as a low-severity finding.
