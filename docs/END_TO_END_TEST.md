# PactPay Arena — First End-to-End Transaction: What Was Tested, and What Was Not

Run date: 2026-10-13. Companion: [PAYPAL_INTEGRATION.md](PAYPAL_INTEGRATION.md) (endpoints, state mapping, §15 to §17 implementation notes), [TRANSACTION_STATE_MACHINE.md](TRANSACTION_STATE_MACHINE.md).

## 0. The one-paragraph answer

**No step of this journey has been run against the real PayPal sandbox.** There are no PayPal sandbox credentials, no sandbox business account id, no webhook id, no public HTTPS address and no sandbox buyer login in this environment, so a live run was not possible and nothing below is labelled "verified live". What _was_ run is the complete journey (offer, policy evaluation, order, buyer approval, hold, capture, webhooks, duplicates, history) through the real application code (routes, services, policy engine, SQLite database, PayPal client, webhook verifier) against **test doubles** that stand in for PayPal. That shows how this code behaves when PayPal answers in the shapes PayPal documents. It does not show that PayPal answers that way.

## 3. Webhook behaviour tested (MOCKED: scripted verifier and fake PayPal)

Tests: `test/payments/webhook-flow.test.ts` (service level), `webhook-api.test.ts` (route + real client + fake PayPal over HTTP), `webhook-verifier.test.ts` (the postback request), and the schema guards in `webhook-flow.test.ts`. Each row is an automated test that passed on 2026-10-13 (counts in section 7).

| Requirement                            | What was shown                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Verify before trusting                 | The verdict comes from PayPal's verification service (postback), with the webhook id from OUR configuration and the body byte for byte. `REJECTED` → 401, no row, no read, no state change. A verification service that cannot be reached → 503 retry, nothing stored. Not configured → 503. A forged delivery cannot squat an event id and block the genuine one. |
| Malformed input                        | Missing or illegal headers, a certificate URL that is http, on another host or a look-alike host, a stale or future transmission time, a non-JSON or non-object body, an event without an id, and an oversized body are all refused before any network call.                                                                                                       |
| Duplicates                             | The same event again → 200 `DUPLICATE`, no second read, no state change, deliveries counted. Six simultaneous copies → one processed, five told to retry. The same event id with different content → 409, never processed.                                                                                                                                         |
| Persist ids and status                 | `webhook_events`: event id, type, resource id, order id, transaction id, payload hash (not the payload), status (`PROCESSING` / `PROCESSED` / `IGNORED` / `FAILED`), reason code, attempts, deliveries, timestamps. The database refuses deletes, edits to final rows, forged attempt counts and a second row for one event id.                                    |
| Reconcile with verified external state | A verified event is only a trigger: the order is read and the read is applied through the same rules as a status check. Examples: a lost capture response and a lost authorization response are each settled by their webhook with no operator action; a refund webhook makes the payment `REVERSED`.                                                              |
| Unexpected / out-of-order events       | Unsupported type, no order id, unknown order, finished transaction → `IGNORED` with no read where possible. Old news (`SUPERSEDED`), contradicted (`CONTRADICTED`) and unconfirmable (`CAPTURE.REVERSED`) events change nothing. An event ahead of PayPal's read → 503 retry, then `IGNORED` after 5 attempts; it never marks anything paid.                       |
| Retry after processing failure         | PayPal unreadable → `FAILED`, 503; the redelivery is processed (attempts 2). An abandoned claim is taken over after 5 minutes; a fresh one is left alone.                                                                                                                                                                                                          |
| Browser redirects                      | An unsigned success redirect (and an unsigned webhook) never moves state; the same journey step with a signed webhook plus a read does.                                                                                                                                                                                                                            |
| No secrets in logs, rows, responses    | Nothing in the webhook path logs. Responses carry only `{status, reason}`. Tests scan the rows, audit payloads and responses for secrets, the signature and the access token.                                                                                                                                                                                      |

## 4. How safe is "mocked"? What the doubles cannot prove

The fakes follow PayPal's documented shapes, and the code under test follows the same documents, so the two can agree with each other and both be wrong. These are the specific things only a live run can settle (they are Q1 to Q9 of PAYPAL_INTEGRATION.md §12.2 plus the webhook-specific ones):

1. Whether PayPal's `verify-webhook-signature` accepts a real sandbox delivery sent exactly as this code builds it, and what it answers for the headers actually received.
2. The real `paypal-cert-url` host. This code refuses anything not on `*.paypal.com`; if real sandbox URLs use another domain every real delivery would be refused (fail-closed).
3. The exact field paths of real events. The order id of an authorization or capture event is read from `resource.supplementary_data.related_ids.order_id` (from PayPal's OpenAPI examples). If a real event lacks it, the event is `IGNORED` with `NO_ORDER_ID` and the payment is settled by a status check instead.
4. Whether the order read shows a capture/authorization immediately after a webhook announces it (the code retries "ahead of the read" events up to 5 times).
5. Whether the webhook simulator's mock events are usable: PayPal documents that postback verification does not support them, so this code rejects them.
6. Everything in PAYPAL_INTEGRATION.md §15.6 and §16.7 that concerns payload shapes, statuses and idempotent replays.
