# Deploying PactPay Arena (public demo on Render)

**Status: prepared and rehearsed locally; NOT deployed.** No public URL exists, and nothing in this document has been run on Render. Section 11 says exactly what was verified and what was not, and section 10 lists the steps that need your Render account.

## 1. What the app needs (found by inspecting it)

| Need              | Finding                                                                                                                                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime           | Node 22.18+ (`node:sqlite`, and native TypeScript for `scripts/*.ts`; tested on 24.18.0). Pinned in `.node-version` and `render.yaml`.                                                                                              |
| Server            | `next start` (Next.js 16). Server-rendered pages and route handlers; no static export, so a static host will not do.                                                                                                                |
| Database          | One **SQLite file** owned by one process. No external database. Migrations are SQL files applied in order.                                                                                                                          |
| State in memory   | Login throttle, webhook verification cap, public-page cap. They are per process, so **one instance only**.                                                                                                                          |
| External services | None required. PayPal Sandbox (optional) and an AI model provider (optional, off by default) are called only from the server, only when the signed-in operator starts a step.                                                       |
| Credentials       | The operator passcode (required). PayPal sandbox client id/secret/merchant id/webhook id (optional). A model key (optional, not configured in the Blueprint).                                                                       |
| Anonymous surface | Pages: Start, Arena, Replay, Cockpit (benchmark rows only), and the shells of the Mandate and Negotiations pages. API: `health`, the simulations, `cockpit` (benchmark part), login, webhook (PayPal-signed). Section 7 lists them. |

Why Render's Node web service and not a serverless host: the SQLite file and the in-process limits need one long-running process with a disk.

## 2. Commands

| Purpose           | Command                                                | Notes                                                                                       |
| ----------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Build             | `npm ci --include=dev && npm run build`                | `--include=dev` because the build needs TypeScript and the type packages (devDependencies). |
| Start             | `npm run start:demo`                                   | `node scripts/start.ts`: validate, migrate, seed, then `next start -H 0.0.0.0 -p $PORT`.    |
| Health check path | `/api/health`                                          | 200 when it can serve, otherwise 503 (section 5).                                           |
| Local development | `npm run dev`, `npm run db:migrate`, `npm run db:seed` | Unchanged. `DEPLOY_MODE` defaults to `local`.                                               |

`DEPLOY_MODE=demo` must be set at **build** time as well as at run time: response headers are fixed when the app is built. `render.yaml` sets it once and Render passes service variables to both.

## 3. Environment variables

Set in `render.yaml` (no secret values in the file) or the Render dashboard. Everything is read by one module on the server (`src/server/env.ts`); nothing is `NEXT_PUBLIC_` and a test fails if the Blueprint contains one.

| Variable                                   | Hosted demo               | Secret? | Notes                                                                                                                       |
| ------------------------------------------ | ------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------- |
| `DEPLOY_MODE`                              | `demo` (in `render.yaml`) | no      | Enables the startup checks and demo protections. Default `local`.                                                           |
| `NODE_ENV`                                 | `production`              | no      | The start script refuses demo mode otherwise.                                                                               |
| `NODE_VERSION`                             | `24.18.0`                 | no      | Render reads it. Matches `.node-version`.                                                                                   |
| `APP_BASE_URL`                             | not set                   | no      | Falls back to Render's `RENDER_EXTERNAL_URL` in demo mode. Set it only for a custom domain. Must be `https`, not localhost. |
| `OPERATOR_PASSCODE`                        | `generateValue: true`     | **yes** | Generated by Render, shown only in the dashboard (Environment). At least 16 characters. Required in demo mode.              |
| `DATABASE_PATH`                            | `./data/pactpay.db`       | no      | Ephemeral on the free plan. `/var/data/pactpay.db` with a persistent disk (section 4).                                      |
| `AGENT_MODE`                               | `scripted`                | no      | Deterministic mock agents. `llm` needs a key and is not enabled by the Blueprint.                                           |
| `PAYPAL_ENV`                               | `sandbox`                 | no      | Only value accepted, in every mode. Live PayPal is refused at startup.                                                      |
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` | `sync: false` (prompted)  | **yes** | Optional; set both or neither. Without them the payment step says it cannot start.                                          |
| `PAYPAL_MERCHANT_ID`                       | `sync: false`             | no      | The sandbox business account that must receive the funds. Without it authorization is refused.                              |
| `PAYPAL_WEBHOOK_ID`                        | `sync: false`             | **yes** | Optional; without it the webhook endpoint answers 503 and trusts nothing.                                                   |
| `PORT`                                     | set by Render             | no      | Validated (1 to 65535).                                                                                                     |

If the dashboard insists on a value for a `sync: false` variable you do not have, enter `replace-with-later`: values with that prefix count as unset. Render prompts for `sync: false` values only when the Blueprint is first created (per Render's documentation); to add them later, use the dashboard.

## 4. Database and migration strategy

- **Migrations run at startup, by the one process that owns the file** (`prepareDatabase` in `src/adapters/sqlite/bootstrap.ts`, called by `scripts/start.ts`): create the directory and file if missing, apply every pending migration in order (idempotent), add the synthetic demo data (two made-up sellers and one mandate; idempotent; no credentials), then verify the audit chain. A chain that does not verify stops the start. Nothing migrates from a request.
- **Free plan: the data is ephemeral.** Render states that a free web service's local files, including SQLite databases, are lost on every redeploy, restart and idle spin-down (it spins down after 15 minutes without traffic, and takes about a minute to start again). Each start therefore begins from a freshly migrated and seeded database. That suits a throwaway demo and is the default in `render.yaml`. Session cookies survive a restart (they are signed with the passcode), but negotiations and audit history do not.
- **To keep data:** use a paid plan with a persistent disk: replace `plan: free` with `plan: starter`, uncomment the `disk` block (mount `/var/data`) and set `DATABASE_PATH=/var/data/pactpay.db`. A disk binds the service to one instance, which this design requires anyway. Back up by downloading the file through a Render shell or disk snapshot; there is no automatic backup.
- **Rollback.** Migrations only add. To go back to an earlier version of the code, redeploy it: an older build refuses to start on a database that has migrations it does not have (the migrator stops with an error rather than guessing), and the start script then exits without serving. To start clean, delete the database file (or the disk's contents) and restart.
- **Never scale beyond one instance.** Two processes would write one SQLite file and each keep its own limits.

## 5. Health checks

`GET /api/health` returns `status: "ok"` with 200 when the service can serve and `status: "degraded"` with 503 otherwise: the database is broken, or (in demo mode) not migrated, or the configuration is invalid (that case lists variable names and messages, never values). It reports flags and counts only (PayPal credentials present or absent, agent mode, migration count) and no secret, path or value. Render uses the health check to decide whether a new deploy is ready (see its health-check documentation for what it does with a running instance that starts failing; that was not tested here).

## 6. Logging, error handling and startup validation

- **Startup validation.** `scripts/start.ts` reads only the process environment (no `.env` file is loaded), validates it, and **refuses to start** (exit 1) with variable names and messages: an invalid value, demo mode without an https public URL or without an operator passcode, `NODE_ENV` not `production` in demo mode, an invalid `PORT`, a database that cannot be created or migrated, a chain that does not verify. It creates nothing when it refuses. One line is printed on success: mode, port, public host, database counts, and yes/no flags for the operator passcode, PayPal credentials, webhook id and agent mode. No value, path or secret.
- **Request logging.** The application writes no per-request logs, and none of its code logs a header, a body, a token or a credential. A test captures every response, log line and database row of a full payment flow with marked secrets and finds none.
- **Errors.** Unknown errors become a bare `500` with a fixed message (no stack, no path); PayPal failures carry only a kind, an HTTP status and PayPal's debug id. The page-level error screen prints a reference, never the error's text. Next.js itself prints unhandled server errors to stderr on the platform (they can include file paths and stack frames, not request data); treat the platform's logs as private to the account owner.
- **Proxy awareness.** Started with `-H 0.0.0.0` (as the start script does), the server's own view of its URL is `http://0.0.0.0:<port>`, whatever `Host` the client sent (observed, see section 11). The browser's `Origin` behind Render is the public `https` URL, so the original same-origin check **would have refused every operator login and write on Render with a 403**. The check now also accepts the configured public origin (`APP_BASE_URL`) and nothing else, and the PayPal return redirect is built from `APP_BASE_URL`, not from the request. Both are tested.

## 7. Demo mode and what an anonymous visitor can reach

Demo mode works **without any privileged credential**: the PayPal variables are optional, the agents are the deterministic mocks, and the data is synthetic. Two tours:

- **No credentials needed (anyone):** Start, the Arena (unsafe baseline versus protected buyer on a simulated ledger), the Replay of the budget-escalation attack, and the Cockpit with its Analytics over the persisted benchmark runs.
- **Operator tour (needs the passcode):** set the mandate, submit a task, run the agents, accept an offer and watch the policy engine decide, see the payment step, inspect the audit history. With PayPal sandbox credentials configured the payment step runs against the sandbox; without them it says it cannot start and nothing is simulated in its place.

| Anonymous request                                                           | Result                                                                                     |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `/`, `/arena`, `/flagship`, `/cockpit`, `/mandate`, `/negotiations` (pages) | 200; the last two show only a sign-in form, their data needs the operator session          |
| `/api/flagship`, `/api/arena/*`, `/api/cockpit`, `/api/health`              | 200; simulations on throwaway data, benchmark rows only (database rows are locked), status |
| `/api/operator/session`                                                     | login, throttled (5 failures a minute, global)                                             |
| `/api/webhooks/paypal`                                                      | accepts only PayPal-signed deliveries (503 until a webhook id is configured)               |
| Every mandate, negotiation, payment, journey and PayPal-return route        | **401**. Payment and administrative endpoints are never exposed to anonymous callers.      |

## 8. Protections for the demo environment

- Everything that can spend, approve or change anything needs the operator's signed session, a CSRF token and a same-origin request; agents are refused even with a cookie (reviewed in [SECURITY_REVIEW.md](SECURITY_REVIEW.md); route sweep in `test/security`).
- Public pages that cost CPU (the replay, about 40 ms each, and the Cockpit) share a **global cap of 240 requests a minute**; beyond it they answer `429` (API) or show a "busy" note (pages). The operator's routes are not affected. This keeps a casual script from keeping a small instance busy; it is not DDoS protection.
- Bounded request bodies (16 KiB for operator JSON, 256 KiB for webhooks), a cap on PayPal verification calls, a login throttle.
- Demo-mode response headers: HSTS (180 days, no subdomains), `X-Robots-Tag: noindex, nofollow`, plus `X-Frame-Options: DENY`, `nosniff`, a restrictive `Permissions-Policy`, and no `X-Powered-By`. The session cookie is `HttpOnly; SameSite=Lax; Secure`.
- A "Public demo" marker in every page header, next to "PayPal Sandbox only" and "Synthetic data".
- PayPal is sandbox-only in every mode (a hard startup error otherwise). A demo can never move real money.

## 9. Test and production configuration are separate

- `.env.example` (committed, placeholders only, `DEPLOY_MODE=local`) is for development. `.env*` files are git-ignored, and the hosted start script never loads them.
- `render.yaml` (committed, no secret values) is for the hosted demo. Secrets live only in the Render dashboard.
- The test suite sets its own environment per test and never reads either. A test checks that the Blueprint holds no secret, uses only commands and paths that exist, and pins the Node version consistently.
- "Production" here means a **public sandbox demo**. This project does not support live PayPal, and this document is not a go-live checklist for real payments.

## 10. Steps that need you (what I could not do)

I have no Render account or API key, the project folder is not a Git repository, and Render builds from a Git repository. I did not create one or push anything. To deploy:

1. Put the project in a Git repository on GitHub, GitLab or Bitbucket (this folder has no `.git`). Do not commit `.env*` or any `*.db` (they are git-ignored).
2. In Render: **New → Blueprint**, choose the repository; Render reads `render.yaml`. Enter `replace-with-later` (or leave blank if allowed) for the four PayPal prompts, or enter your sandbox values.
3. After the first deploy: read `OPERATOR_PASSCODE` in the service's Environment tab, and note the `https://<name>.onrender.com` URL.
4. Check, in this order: `GET <url>/api/health` is 200 with `"deployMode":"demo"`; the Start page loads and shows the "Public demo" chip; then run the main demo flow against the URL with `VERIFY_URL=<url> OPERATOR_PASSCODE=<passcode> npm run verify:deployment` (31 checks since the Live model page was added; it creates one synthetic negotiation). Record its output.
5. **Making the hosted demo useful to judges.** Without PayPal values the payment step says it cannot start; with the four sandbox values entered the server creates real sandbox orders, but a judge cannot approve one without a sandbox buyer login. Either put the sandbox Personal (buyer) account's login in the submission's testing instructions (sandbox accounts are synthetic) or leave PayPal off and let judges use the Arena, the flagship replay, the Cockpit and the Live model page, which need nothing. Share the `OPERATOR_PASSCODE` from the dashboard in the testing instructions for the operator pages. Keep `AGENT_MODE=scripted`: a shared model key on a public demo would be rate-limited (8000 tokens per minute on Groq's free tier) and spendable by anyone with the passcode.
6. For the PayPal sandbox (optional, **not verified on Render**): create a sandbox REST app and a webhook listener for `<url>/api/webhooks/paypal`, put the client id, secret, webhook id and the sandbox business account id into the dashboard, redeploy, and run `npm run paypal:smoke` locally first.

### Not verified (do not read any of this as working)

- **Nothing was deployed. There is no public URL, and no deploy, build or health check ran on Render.** The Blueprint was checked against Render's published Blueprint specification, environment-variable and free-plan pages (keys `autoDeployTrigger`, `generateValue`, `sync: false`, `healthCheckPath`, `RENDER_EXTERNAL_URL`, the ephemeral free filesystem and the 15-minute spin-down), not by Render itself.
- **Behaviour behind Render's real proxy** was simulated with headers on a local port, not observed. What was observed locally (see the origin probe below) is that the server ignores the `Host` header when forming its own URL, which is why the origin fix was needed; whether Render's proxy forwards `Origin` unchanged to the app is the standard behaviour but was not checked on Render.
- **Browsers over the real HTTPS URL** (the `Secure` cookie, HSTS) were not exercised; the `Secure` attribute was observed on the response header only.
- **The PayPal sandbox** (order, approval, hold, capture, webhook delivery) was not exercised: no sandbox credentials exist here. Those steps are covered only by the fake-PayPal tests.
- **Cold start timing, free-plan memory limits and idle spin-down** were not measured. The first request after idle can take about a minute on the free plan (Render's documentation): warm the URL before a demo.
- **Load.** The public cap was tested for correctness, not under load.

## 12. Security implications reviewed before deploying

| Concern                            | Assessment                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Anonymous access to money or admin | None: every spending, approval and administrative route needs the operator session (section 7). Verified over HTTP in the rehearsal.                                                                                                                                                                                                                                                                                                                   |
| The shared operator passcode       | The one real credential of a public demo. Generated by Render (high entropy), never in the repository, never logged. It is shared with whoever you let operate the demo; **anyone holding it can run the operator tour**, including with PayPal sandbox credentials if you set them. Rotate it (dashboard → Environment → regenerate) after the demo; that signs everyone out. Sessions cannot be revoked individually (SECURITY_REVIEW limitation 4). |

Accepted for a demo; the operator routes keep working.                                                                                                                                                                                                                                                                                                          |
