## 2. The chosen flow, and why capture and payout are different things

1. **Charge path (Orders v2 + Payments v2).** The buyer pays the **merchant** (the business account that owns the REST app). `intent=AUTHORIZE` places a hold after the buyer approves; a later _capture_ turns the hold into a charge, or a _void_ releases it. Capture moves money **buyer → the app's merchant account**. [DOC]
2. **Seller path (Payouts v1, optional).** Paying a _seller_ out of the merchant's balance is a **separate API, a separate OAuth scope, a separate account approval, separate webhooks and separate identifiers** (§9). A successful capture does not pay anyone, and a payout is not evidence of a capture.
3. **No escrow.** Nothing in Orders or Payments v2 is an escrow product. An authorization is a time-limited hold on the buyer's funding source, which can lapse or be declined for risk at capture time. [DOC: honor period and `PENDING`/`DENIED` reasons, §6]
4. **No split to a third-party seller in this design.** Orders v2 only splits funds to another merchant through `payment_instruction.platform_fees` / `disbursement_mode`, which the spec ties to PayPal Complete Payments Platform enablement (ARCHITECTURE V9). We have no such enablement, so sellers in the Arena are _logical_ identities and the real money goes to one sandbox merchant. See §10.

## 4. OAuth access token

| Item       | Documented value                                                                                                                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request    | `POST https://api-m.sandbox.paypal.com/v1/oauth2/token`; header `Content-Type: application/x-www-form-urlencoded`; HTTP Basic auth with `CLIENT_ID:CLIENT_SECRET`; body `grant_type=client_credentials`. [DOC] |
| Response   | JSON with `access_token`, `token_type` (sample: `Bearer`), `expires_in` (seconds; sample 31668, about 8.8 hours), `scope` (space-separated permission URIs), `app_id`, `nonce`. [DOC]                          |
| Use        | `Authorization: Bearer <access_token>` on later calls. When it expires, request a new one. [DOC]                                                                                                               |
| Not stated | A fixed lifetime (only the sample value), caching guidance, and rate limits for the token endpoint. [NOT STATED]                                                                                               |

**Scopes the operations declare** (from the OpenAPI `security` entries): Orders create / show / authorize use `https://uri.paypal.com/services/payments/payment` (the spec also lists `.../payments/orders/deprecating-jssdk-migration-for-limited-merchants` on the same requirement); Payments v2 show / capture / void / reauthorize use `https://uri.paypal.com/services/payments/payment/authcapture`; webhook verification and webhook management use `.../applications/webhooks` (and `.../applications/verify-webhook-signature` for the verify call); Payouts uses `https://uri.paypal.com/payments/payouts`. **Which of these a default sandbox REST app is actually granted is unknown** until a token is requested [UNVERIFIED]: the smoke test (§12.2) must compare the `scope` field of the real response with this list.

Implementation rules carried into the future adapter: cache the token in memory only, refresh before `expires_in` (with margin) and once on a 401; never log the token, the Basic header or the secret; redact `Authorization` in every error path; refuse to start unless the env guard passes.

### 6.3 Timing and expiry

| Fact                                                                                                                                                                                                                                                                     | Source                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| Authorized payments are best captured within **three days** (the honor period) and are available to capture for up to **29 days**; after the honor period "the original authorized payment expires and you must re-authorize".                                           | Orders spec [DOC]      |
| Reauthorization is rejected inside the honor period (documented 422 example) and restarts a 3-day honor period; after 30 days from the original authorization you must create a new authorization.                                                                       | Payments spec [DOC]    |
| The `authorization` object has an `expiration_time` field ("when the authorized payment expires"). Which of the 3-day / 29-day / 30-day instants it denotes, and whether it is populated in the sandbox, is **[NOT STATED]**; the official sample is inconsistent (§11). | Payments spec          |
| `PAYMENT.AUTHORIZATION.VOIDED` is sent for a manual void **and** when the "30 day validity period" ends (Payments v2).                                                                                                                                                   | Event-names page [DOC] |
| Order approval: 6 h to redirect + 6 h to approve and authorize (defaults).                                                                                                                                                                                               | Orders spec [DOC]      |
| `ORDER_EXPIRED` exists as an authorize error; the validity period of an order is **[NOT STATED]** beyond the approval windows above.                                                                                                                                     | Errors page            |

Design consequence: keep computing `honorExpiresAt` locally with the injected clock (as in the state machine) and use `expiration_time` only as a recorded observation that can make us _more_ conservative (`min`), never later. Expiry cannot be observed in the sandbox within the project's timeline, so expiry handling stays **tested only with the injected clock**.

## 7. Idempotency and request identifiers

| Topic                           | Documented                                                                                                                                                                                                                                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Header                          | `PayPal-Request-Id`, optional, on REST **POST** calls "a unique user-generated ID that the server stores for a period of time". Not every API supports it. Create order, authorize order, capture, void and reauthorize declare it in their specs. [DOC]                                                                    |
| Same key, same request          | Returns "the latest status of the previous request" instead of repeating the action (a retried capture shows the capture, not a second charge). Replay status codes: spec text says 200 for an idempotent replay of authorize/capture; the guide's example shows 201 → accept **either** 200 or 201. [DOC, partly CONFLICT] |
| Concurrent same key             | PayPal "processes the first request and might fail the second". [DOC]                                                                                                                                                                                                                                                       |
| No header                       | "PayPal duplicates the request." [DOC] → we always send one.                                                                                                                                                                                                                                                                |
| Key uniqueness                  | Unique per request **and per API call type** (authorize and capture need different keys). UUIDs recommended and described as meeting a "38 single-byte character" limit; the OpenAPI parameter allows up to 10,000 characters. [DOC, CONFLICT-ish]                                                                          |
| Retention                       | **[NOT STATED]** on the idempotency page. Other official text: Payouts keys are stored 30 days; the requests guide gives a refund example "up to 45 days". Nothing authoritative for Orders create/authorize/capture/void.                                                                                                  |
| Same key, different body        | **[NOT STATED]**.                                                                                                                                                                                                                                                                                                           |
| Retry guidance                  | Safe to retry after network timeouts or 5xx while the key is retained. [DOC]                                                                                                                                                                                                                                                |
| Create order + `payment_source` | `PAYPAL_REQUEST_ID_REQUIRED`: the header is mandatory when a `payment_source` is sent. [DOC]                                                                                                                                                                                                                                |

**Our identifiers.** (1) `PayPal-Request-Id`: one per attempt, stable across retries of the same attempt, different per action; keep it **≤ 38 bytes** to stay inside the documented UUID-sized limit, for example a UUID derived deterministically from `tx id + action + sequence` (the current design string `pp:{tx}:{action}:{seq}` should be hashed or shortened if it exceeds 38). (2) `custom_id` = our transaction id (reconciliation; not shown to the payer). (3) `invoice_id` = unique per transaction attempt (PayPal rejects duplicates by default; the buyer sees it). (4) `reference_id` may be left to default (`default`). (5) PayPal's own ids (`order id`, `authorization id`, `capture id`) are stored with the attempt; the error body's `debug_id` is stored for support. Because retention and different-body behaviour are not documented, **PayPal idempotency stays secondary**: the local unique index plus GET-before-retry remain the primary guard (unchanged from the architecture).

## 8. Webhooks

| Registration          | Developer Dashboard → the app's settings → subscribe a listener URL and event types (or `POST /v1/notifications/webhooks` with `url` and `event_types`; scope `.../applications/webhooks`). Record the generated **Webhook ID**; it is required to verify every message to that URL. Up to 10 URLs per app; each URL receives only that app's events.                                                                                     |

Localhost is not reachable by PayPal (the guide's sample uses localhost:8888 behind a forwarding setup). **We need a public HTTPS URL.**                                                                                                                                                                                                                                             |
| Retries               | Non-2xx → retried up to **25 times over 3 days**; then marked Failed (manual resend from the dashboard). Intervals [NOT STATED]. Therefore duplicates are expected.                                                                                                                                                                                                                                                                       |
| Headers               | `paypal-transmission-id`, `paypal-transmission-time`, `paypal-cert-url`, `paypal-transmission-sig` (and the auth-algorithm header named `PAYPAL-AUTH-ALGO` in the verify API reference).                                                                                                                                                                                                                                                  |
| Offline verification  | Build `transmissionId \| timestamp \| webhookId \| crc32`, where `crc32` is the **decimal CRC32 of the raw, unparsed request body** (the guide warns against re-serialising JSON); download the certificate from `paypal-cert-url`, cache it, verify the base64 signature with SHA256 (RSA). | Events we need        | `CHECKOUT.ORDER.APPROVED`; `PAYMENT.AUTHORIZATION.CREATED`; `PAYMENT.AUTHORIZATION.VOIDED` (manual void **or** validity lapse); `PAYMENT.CAPTURE.COMPLETED`, `.DECLINED`, `.PENDING`, `.REFUNDED`, `.REVERSED`. `CHECKOUT.ORDER.COMPLETED` is described as for marketplaces/platforms only; no `CHECKOUT.ORDER.VOIDED` event is listed.                                                                                                   |
| Not stated            | Certificate-chain validation and cache-expiry guidance; the allowed `paypal-cert-url` hosts; event-id deduplication guidance; payload ordering guarantees; sandbox-vs-live differences in delivery. [NOT STATED]                                                                                                                                                                                                                          |

**Requirements this places on our implementation (our hardening, not PayPal-documented):** verify against the raw bytes before any JSON parse; refuse to fetch a certificate from a host that is not on an explicit PayPal allow-list (the allow-list values must come from real sandbox deliveries, §12); require HTTPS; treat the event `id` as the dedupe key (`UNIQUE(paypal_event_id)`); an unverified or unverifiable event never changes state; a verified event is only a **trigger**, and the state change comes from a fresh authenticated GET (so a stale or replayed valid event cannot regress state).

## 9. Payouts is separate, and its access is unresolved

| Topic                 | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What it is            | `POST /v1/payments/payouts` creates a **batch** (`sender_batch_header`, `items[]` with `receiver`, `amount {currency, value}`) paid from the merchant's **PayPal balance** to recipients (email, phone, PayPal id or handle). Item and batch statuses are separate from capture states; webhooks are `PAYMENT.PAYOUTSBATCH.*` and `PAYMENT.PAYOUTS-ITEM.*`. Related endpoints: show batch, show item, cancel unclaimed item.                                                                                                        |
| Scope                 | `https://uri.paypal.com/payments/payouts` (not one of the Orders / Payments scopes).                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Idempotency           | `sender_batch_header.sender_batch_id`: a reused id within 30 days is rejected with a link to the original; the `PayPal-Request-Id` header keys are stored 30 days. ## 11. Inconsistencies in PayPal's own documentation (do not "resolve" by guessing)

1. **Reauthorization count:** the Payments v2 operation text says multiple reauthorizations are possible within the 29-day period; the `reauthorize_request` schema text says "only once" (days four to 29). The checkout guide says "multiple". → Out of MVP; if ever built, test in the sandbox.
2. **Validity length:** capture is "up to 29 days", reauthorize talks about "30 days since the original authorization", and the webhook description gives a "30 day validity period". → Treat the honor period (3 days) as the only reliable bound; handle later lapse as an observed `VOIDED`.
3. **`expiration_time` sample** in the checkout guide is earlier than its `create_time`. → Do not rely on that field's value without a real observation.
4. **Replay status code:** spec text says 200 for an idempotent replay, while the idempotency guide's example shows 201. → Accept both.
5. **Void response:** 204 normally, 200 only with `Prefer: return=representation`. → Handle both.
6. **PayPal-Request-Id length:** OpenAPI parameter up to 10,000 characters vs the guide's "38 single-byte characters" for UUIDs. → Stay under 38.

### 15.3 The flow as implemented

```
operator: Start            POST /api/negotiations/{id}/payment            (empty body)
  server:  load ACTIVE agreement + transaction (amount, currency, payee_ref, agreement version)   [stored rows]
           policy engine CREATE_ORDER (approval, mandate, budget, payee, state)  → DENY ends here, nothing is sent
           ONE db transaction: AGREED → CREATING_ORDER + attempt CREATE_ORDER #n (request id pp:{tx}:CREATE_ORDER:{n})
           POST /v2/checkout/orders  intent=AUTHORIZE, one unit, amount "80.00", custom_id = tx id, invoice_id = INV-{tx}-{n}
           GET  /v2/checkout/orders/{id}            ← the order is believed only after it matches our records
           ONE db transaction: CREATING_ORDER → ORDER_CREATED (order id stored)         | mismatch/ambiguity → NEEDS_RECONCILIATION
buyer:   opens the approval link (new tab), logs in as the sandbox buyer, approves     (human, at PayPal)
buyer:   is redirected to GET /api/paypal/return?token={order id}     ← UNTRUSTED: only a lookup key; the server then asks PayPal
  server:  GET /v2/checkout/orders/{id}  → APPROVED → ORDER_CREATED → ORDER_APPROVED  (still nothing held)
operator: Authorize        POST /api/negotiations/{id}/payment/authorize   (empty body)
  server:  GET order (fresh) → must match records and be APPROVED
           policy engine AUTHORIZE with the observed amount/currency/payee
           ONE db transaction: ORDER_APPROVED → AUTHORIZING + attempt AUTHORIZE #n
           POST /v2/checkout/orders/{id}/authorize           (PayPal-Request-Id = pp:{tx}:AUTHORIZE:{n})
           GET  /v2/checkout/orders/{id}            ← authorization CREATED + same amount/currency → AUTHORIZED (hold, not a charge)
                                                       PENDING → AUTHORIZATION_PENDING, DENIED → FAILED, anything else → NEEDS_RECONCILIATION
```

The honor period is recorded as `min(PayPal create_time, our observation time) + 3 days`.

### 15.4 What each failure does

| Event                                                                                                      | Result                                                                                                                                                                         |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Network loss, timeout, 429, 5xx, 409, 202/207, unparseable answer, credentials rejected                    | `NEEDS_RECONCILIATION`, attempt `UNKNOWN`. Never success, never a failure that frees the budget.                                                                               |
| A refusal that proves nothing happened (400/403/404/422 without an "already happened" issue)               | `FAILED` (terminal), attempt `FAILED_DEFINITE`. Nothing charged.                                                                                                               |
| A refusal that says something already happened (`ORDER_ALREADY_AUTHORIZED`, `DUPLICATE_INVOICE_ID`, ...)   | Treated as unknown and reconciled by a read.                                                                                                                                   |
| 2xx but PayPal's order differs in amount, currency, `custom_id`, `invoice_id`, intent, unit count or payee | `NEEDS_RECONCILIATION` + `PAYPAL_ANOMALY` audit event; the order can never be authorized.                                                                                      |
| Response lost after PayPal did act                                                                         | "Check status": a create is re-sent with the **same** `PayPal-Request-Id` (at most 3 tries, then `FAILED`); an authorize is settled by READING the order, never by re-sending. |
| Order `COMPLETED`                                                                                          | Never read as success by itself; only the authorization inside it counts.                                                                                                      |
| Double click / concurrent requests                                                                         | The second finds the transaction already out of `AGREED` / `ORDER_APPROVED` and sends nothing.                                                                                 |

### 15.6 Remaining gaps (honest list)

1. **Nothing here has touched the real PayPal.** Treat the first live run as the actual test; expect to find at least one shape or permission mismatch (Q1–Q9).
2. **(Capture and void now exist: §16; webhooks now exist: §17.) No refund, reauthorize or payout.** The hold can lapse and nothing records it (`AUTHORIZED → VOIDED` is not a legal transition without a void call); there is no webhook endpoint, so PayPal-initiated changes are seen only when someone presses "Check status". Verified webhooks, capture ("release funds") and void are the next slice. Payouts stay a separate, unbuilt, simulation-only item (§9).
3. **A definite refusal is terminal** (`FAILED` has no exit in the state machine): a typo-class bug in our request would burn that agreement and require a new negotiation. This follows the state machine; revisit before real use.
4. **USD only** (the sandbox support of other currencies is unverified), **one purchase unit**, **full amount only**.
5. **The payee is the single configured merchant.** Sellers are logical identities (`payee_ref`); the policy engine's payee check receives "the logical payee" only when PayPal's `merchant_id` equals `PAYPAL_MERCHANT_ID`. If PayPal does not echo the payee at all (unverified, A3), authorization is refused rather than assumed.
6. **The approval link is not persisted as a column**: it is kept in the audit event of the observation. If PayPal does not return an `approve` link on read-back, the operator can only use the link from the create step.
7. **The return redirect needs the operator's browser session** (it is operator-only). A cross-site redirect should carry a `SameSite=Lax` cookie on a top-level GET; whether the app's session cookie is configured to be sent is unverified.
8. **Single process, single SQLite writer** (unchanged), and no automatic reconciliation timer: unknown outcomes are settled when the operator presses "Check status" (the state machine's background backoff schedule is not built).
9. **Request-id length:** production ids give `pp:tx_{14}:CREATE_ORDER:{n}` (35 bytes), inside the documented UUID-sized (38 byte) guidance; PayPal's actual limit is unverified.

### 16.3 Guards before any capture or void request (G2 / G3 of the state machine)

1. **State.** Only `AUTHORIZED` qualifies. A repeat or a race lands on the state that already holds the answer (`CAPTURING`, `CAPTURE_PENDING`, `CAPTURED`; `VOIDING`, `VOIDED`) and sends nothing (`performed: false`). Other states are a 409 with a reason (for example an unresolved earlier request, a released hold, a hold PayPal has not finished authorizing).
2. **Trusted records.** The negotiation's ACTIVE agreement, its transaction, the stored order id, **the stored authorization id**, the agreed total, currency and logical payee are loaded from the database. An agreement whose payment has started cannot be replaced (the negotiation service refuses new offers), so the held payment cannot be orphaned by a new agreement.
3. **Fresh read.** `GET` of the order. It must match the records: order id, intent, one purchase unit, amount, currency, `custom_id`, `invoice_id`, payee (the configured sandbox merchant, reported by PayPal), exactly one authorization **with the stored id** and the agreed amount/currency, and no capture that our records do not account for. Anything else is a recorded `PAYPAL_ANOMALY` and nothing is sent.
4. **Policy engine.** `CAPTURE` (or `VOID`) is evaluated from stored rows plus that observation: operator authority, state, duplicate attempt, a capture already succeeded, mandate integrity and status (a revoked mandate stops a capture; a newer non-revoked version does not, by the policy's recorded decision), the human approval of this agreement, amount/currency/payee against the observation, and the honor period (`now ≥ honorExpiresAt − 1 h` refuses a capture). A `DENY` is persisted with its reason codes and nothing is sent. A void is never refused for the honor period or the mandate: it only reduces exposure.
5. **Write-ahead.** The policy decision, the attempt row (`pp:{tx}:CAPTURE:{n}` / `…:VOID:{n}`) and the state change `AUTHORIZED → CAPTURING/VOIDING` are one database transaction. A concurrent request finds the state moved and sends nothing, so exactly one request is made.
6. **Attempt budget.** At most three capture attempts and three void attempts per payment (the schema's limit); after three refusals the operator is told to release the hold instead.
7. **The request**, outside any database transaction, with that attempt's stable `PayPal-Request-Id`.
8. **Read-back.** The result is believed only after the order is read again and interpreted by the same rules.

### 16.4 What each outcome does

| Event                                                                                                                                                                                                  | Result                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2xx and the read shows a `COMPLETED` full capture on a `CAPTURED` authorization                                                                                                                        | `CAPTURED`; the capture id and amount are stored. This is the only state shown as paid.                                                                                                                                                                              |
| 2xx and the read shows a `PENDING` capture                                                                                                                                                             | `CAPTURE_PENDING`: **not paid**. The attempt stays `UNKNOWN` (not `SUCCEEDED`) so that a later decline can close it as refused and allow one more try. Completion later → `CAPTURED`; a listed decline → `AUTHORIZED`; the hold gone → `FAILED`.                     |
| 2xx but the read shows **no effect** (stale read, or a declined capture)                                                                                                                               | A contradiction, not a failure: `NEEDS_RECONCILIATION`. It is never read as "nothing happened" at once.                                                                                                                                                              |
| Timeout, network loss, 429, 5xx, 409, 202/207, unparseable answer, or a refusal that says something already happened (`PREVIOUSLY_CAPTURED`, `MAX_CAPTURE_AMOUNT_EXCEEDED`, `AUTHORIZATION_VOIDED`, …) | `NEEDS_RECONCILIATION`, attempt `UNKNOWN`. A second capture/void is refused (409) until a status check settles it.                                                                                                                                                   |
| Status check, and the order **shows the capture/void happened**                                                                                                                                        | Applied at once (`CAPTURED`, `VOIDED`, or `CAPTURED` when a void lost a race with a capture).                                                                                                                                                                        |
| Status check, the order shows **no effect**, and the request was sent **less than 60 s ago**                                                                                                           | Nothing changes ("check again shortly"). A slow request must not be followed by a fast second one.                                                                                                                                                                   |
| Status check, no effect, request older than 60 s                                                                                                                                                       | Attempt closed `FAILED_DEFINITE`, state back to `AUTHORIZED`; the next capture/void is a **new attempt** (new request id). PayPal's own amount limit (the capture is the whole authorization) is the last backstop if the earlier request was in fact still pending. |
| A refusal that proves nothing happened (400/403/404/422 without an "already happened" code, e.g. `AUTHORIZATION_EXPIRED`)                                                                              | Attempt `FAILED_DEFINITE`; the hold is read: intact → `AUTHORIZED` (honor clock **not** restarted), voided → `FAILED`. A refused void returns to `AUTHORIZED` through `NEEDS_RECONCILIATION` in the same transaction (the transition table has no direct edge).      |
| The hold is already gone at PayPal and the operator releases                                                                                                                                           | Recorded `VOIDING → VOIDED` **without** sending a void (`PAYPAL_VOID_NOT_NEEDED` is audited). A capture of a gone hold is refused with a note.                                                                                                                       |
| A captured payment later read as refunded/partially refunded                                                                                                                                           | `REVERSED`; no longer shown as paid. (Refunds cannot be started here; they are only recorded.)                                                                                                                                                                       |

### 16.5 Decisions you may want to revisit

- **No `invoice_id` on the capture.** The order already carries ours, and PayPal can refuse a repeated invoice id (`DUPLICATE_INVOICE_ID`). Association is by authorization id and by the order read-back.
- **Only the order read is used as evidence.** `GET /v2/payments/authorizations/{id}` and `GET /v2/payments/captures/{id}` are not called: the order embeds both lists. If the real sandbox shows the order lagging behind those endpoints, add them as a second source.
- **The 60-second quiet period is a heuristic** (the state machine's in-flight timeout). If PayPal's reads lag longer than that, a capture that did happen can be read as "did not", after which a new request is made; PayPal's amount limit should refuse it (`MAX_CAPTURE_AMOUNT_EXCEEDED`, which is then reconciled, never trusted as a failure). A test covers exactly this path.
- **`expiration_time` is not used.** Its meaning is [NOT STATED] (§6.3); the honor period is our own 3-day clock from the first observation, and PayPal's `AUTHORIZATION_EXPIRED` refusal is the backstop.
- **A newer, non-revoked mandate version does not block a capture** of a hold the agreement already froze (policy 1.1.0, `docs/POLICY_ENGINE.md` "Decisions you may want to flip"); revocation does.
- **A capture needs a verifiable payee.** If PayPal stops reporting the merchant, the policy refuses (`PAYEE_MISMATCH`), the same rule as authorization.

1. Complete §15.5 (credentials, `PAYPAL_MERCHANT_ID`, public HTTPS `APP_BASE_URL`), run the app, start a payment, approve as the sandbox buyer, authorize.
2. On the payment panel press **Release the hold (void)** on a first hold. Expected: `VOIDED`; the attempts list shows `void #1: succeeded (HTTP 204)`. Record the HTTP status and what the order status reads afterwards (Q5).
3. Make a second agreement and hold. Press **Capture**. Expected: `CAPTURED`, attempts `capture #1: succeeded (HTTP 201)`. Record the capture's `status`, `final_capture`, whether the authorization reads `CAPTURED`, and the order status (this decides the assumptions in §16.1).
4. Press Capture again and Release on the captured payment. Expected: no new requests; a 409 for the release.
5. Note any `PAYPAL_ANOMALY`, `PAYPAL_OBSERVATION_NOT_APPLIED` or `NEEDS_RECONCILIATION` and the PayPal debug id; each is a mismatch between this document and the real API.

### 16.7 Remaining gaps (honest list)

1. **Nothing here has touched the real PayPal.** The first live capture is the actual test; expect at least one shape or status mismatch.
2. **No webhooks.** A capture completing later, a refund, a dispute or a lapsed hold is noticed only when someone presses "Check status" (or, for a pending capture, a later check). A hold that lapses is **not recorded unless the operator presses Release** (the state table has no `AUTHORIZED → VOIDED` edge); a capture of it is refused.
3. **No automatic reconciliation timer and no automatic void before the honor period ends** (T19 of the state machine). The honor window is enforced only when someone tries to capture.
4. **Full capture only** (one final capture of the whole agreed total). No partial capture, reauthorization, refund or dispute handling.
5. **Capture moves money from the buyer to the configured sandbox merchant, not to the seller.** The seller payout is a separate, unbuilt (and simulation-only) item (§9). A captured payment is not escrow and not a promise of a refund; the screen says so.
6. **A void cannot be started from `AUTHORIZATION_PENDING`** (no authorization id is stored yet) or before authorization; an unfinished order is simply left to expire at PayPal.
7. **A `FAILED` payment is terminal** (a payment whose hold was gone when a capture was attempted cannot be retried; it needs a new negotiation).
8. **Single process, single SQLite writer** (unchanged).

### 17.4 Decisions you may want to revisit

- **Postback, not offline verification.** It needs no certificate handling, but every delivery costs one call to PayPal and fails closed (503) when PayPal is down. Offline verification can be added once real sandbox certificate hosts are known.
- **Simulator mock events cannot be used**: PayPal documents that they are not supported by the postback; they are rejected as `INVALID_SIGNATURE`.
- **A webhook never moves state by itself.** Even a perfectly signed event only triggers a read, and what the read shows is what is applied. A signed event that is ahead of PayPal's own order read is retried, not believed.
- **`*.paypal.com` for `paypal-cert-url`** is our hardening, not a PayPal rule; the value is only forwarded to PayPal.
- **A lapsed hold** (`PAYMENT.AUTHORIZATION.VOIDED` from PayPal's validity timer) is recognised as consistent but cannot be recorded: the state table has no `AUTHORIZED → VOIDED` edge. The operator records it with "Release the hold" (§16).
- **Rejected deliveries are audited at a bounded rate** (20 per minute) so a flood cannot fill the hash-chained trail.

### 17.5 Human steps (cannot be done by this code)

1. Make the app reachable at a public HTTPS URL on port 443 and set `APP_BASE_URL` to it.
2. In the PayPal developer dashboard, create a webhook listener for `https://<host>/api/webhooks/paypal` subscribed to the eight event types in §17.1; copy its **Webhook ID** into `PAYPAL_WEBHOOK_ID`.
3. Run the live runbook in END_TO_END_TEST.md §6 and record every mismatch.

### 17.6 Remaining gaps

1. **Never run against the real PayPal** (verification, payload paths, certificate hosts, read-after-webhook timing).
2. No offline verification; no automatic reconciliation timer (a transaction with no webhook and no operator check stays as it is); no webhook-driven automatic void before the honor period ends.
3. `PAYMENT.CAPTURE.REVERSED` (chargebacks) is recorded but never applied.
4. The history panel lacks `ALLOW` policy decisions and unauthenticated rejections (they belong to no transaction).
5. Single process, single SQLite writer: the "claim" is a database row, so two server processes would still not double-process, but only one process is supported.

### 17.7 The return from PayPal landed on a JSON error (found live, fixed 2026-11-09)

The documented assumption (section 15, point 7) was that the session cookie reaches the return endpoint on a top-level redirect from PayPal. Everything else still worked because the operator could press "Check status with PayPal", which is why this survived the first live runs. Fixed: the cookie is `SameSite=Lax` (sent on a top-level GET navigation, not on cross-site POSTs; mutating routes keep the CSRF token and the `Origin` check), and an unauthenticated return now redirects to the console (`?payment=signin`) instead of printing JSON. The server still reads the order from PayPal only for a signed-in operator.
